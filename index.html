01 / Metod

Gissa mindre.
Testa mer.

När ett nätverk inte fungerar är det lätt att börja ändra saker på måfå. Jag vill istället kunna förklara varför jag gör varje test. Därför börjar jag med att definiera exakt vad som inte fungerar, samlar information om klienten och nätverket och arbetar sedan från det mest grundläggande till det mer specifika.

Hur jag tänker

Om en användare exempelvis säger att "internet inte fungerar" är det egentligen inte tillräckligt specifikt. Jag vill först ta reda på om klienten har en IP-adress, om den når sin gateway, om den kan nå andra nät och om problemet gäller IP-kommunikation eller exempelvis DNS. På så sätt kan ett stort problem delas upp i mindre frågor som går att testa.

02 / Topologi

Var börjar
trafiken?

Topologin är medvetet enkel. Den gör det lättare att följa trafikens väg från klienten till gatewayn och vidare mot ett annat nät. Om klienten kan nå gatewayn men inte servern vet jag redan att vissa delar fungerar — och kan därför fokusera felsökningen på VLAN, routing eller filtrering istället för att kontrollera allt.

03 / Felscenarier

Hitta felet.

Här har jag gjort fyra vanliga problem som små, avgränsade case. Tanken är att visa hur jag skulle gå från ett användarsymptom till konkreta tester. Exemplen är simulerade för projektet, men felsökningslogiken är tänkt att likna hur man kan resonera i ett riktigt support- eller driftärende.

04 / Verktyg

Bevis före
antaganden.

Jag ser kommandona som verktyg för att bekräfta eller avfärda hypoteser. Ett ping-test kan exempelvis visa att IP-connectivity fungerar, men säger inte automatiskt att DNS eller en specifik applikation fungerar. Därför behöver verktyget matcha frågan jag försöker besvara.
